# Mobile Protocol

Rules for `apps/mobile` - the Expo (React Native, TypeScript) app. Shared conventions: [core_protocol.md](core_protocol.md). BLE message shapes: [ble_protocol.md](ble_protocol.md). Alert behavior: [sos_alert_flow.md](../design/sos_alert_flow.md). Visual tokens: [style_guide.md](../design/style_guide.md).

---

## Build model

- **Expo with development builds, not Expo Go.** BLE needs native code, so the app runs as a dev build (`npx expo run:ios|android` or EAS Build). Expo Go cannot connect to the bangle.
- **Native config lives in `app.config.ts` + config plugins** (permissions, background modes, the BLE plugin). Never hand-edit `ios/` or `android/`; they are regenerated by `expo prebuild`.
- **EAS Build / EAS Update** for distribution. An OTA update must never change native config or the BLE protocol version - those need a store build.

## Structure

- `app/` holds expo-router routes only; each route composes a feature from `src/features/<name>/`.
- `src/features/sos/` owns the **alert state machine** - plain TypeScript, no React Native imports, clock injected. UI and BLE feed it events; it emits commands (start cancel countdown, send alert, cancel).
- `src/lib/ble/` is the only place that talks to the BLE library. It turns raw notifications into typed events using `packages/ble-protocol`. Nothing else imports the BLE library.
- `src/lib/supabase.ts` is the single Supabase client. Screens reach data through feature hooks, never by calling the client inline.

## Bluetooth and background behavior (the hard part)

The app must keep a live link to the bangle while backgrounded and detect a lost link quickly. Treat every item below as **verify-on-device, verify-against-current-docs**; OS behavior changes between versions.

- **iOS:** `bluetooth-central` background mode; use CoreBluetooth state restoration (restore identifier) so the OS can relaunch the app for BLE events. Known limitation: iOS does not relaunch an app the user has **force-quit** - the app must detect and warn about this (see open questions in [sos_alert_flow.md](../design/sos_alert_flow.md)).
- **Android:** a **foreground service** (type `connectedDevice`) with a persistent notification keeps the connection alive; request `BLUETOOTH_SCAN` / `BLUETOOTH_CONNECT` (Android 12+) and notification permission (Android 13+). Ask users to exempt the app from battery optimization.
- **Permissions are onboarding steps, not surprises.** Each permission (Bluetooth, notifications, location, background location) gets its own explained screen; a denied permission shows exactly what no longer works.
- **Reconnect automatically** after a drop, and keep reporting link state to the alert state machine. A reconnect inside the grace period cancels the pending alert.
- **Document every platform quirk on discovery** in this file, in the same PR.

## UI rules for a safety app

- **The cancel window is the most important screen.** Full-screen, huge cancel target, countdown visible, haptic + sound, works from the lock screen notification. Never require navigation to cancel.
- **Link and battery status are always visible** on the home screen: connected / reconnecting / lost, battery estimate, and "replace battery within N days" warnings.
- **Never show a silent failure.** If an alert could not be sent (no network, SMS failed), say so immediately and offer the fallback.
- Tokens only (no raw colors or magic numbers); safe-area insets; minimum 44pt touch targets; WCAG AA contrast; test on the smallest supported device.
- **Discreet by default** - notifications and the app name should not reveal "SOS" details on a lock screen that someone else might see, unless the user opts in.

## State and data

- Local UI state for UI concerns; the alert state machine holds alert state; Supabase data through feature hooks. No global store without approval.
- Offline-first for what matters: emergency contacts and alert settings are cached on device so an SOS can still be composed without a network.

## Testing

- Jest (`jest-expo` preset) + React Native Testing Library.
- The alert state machine and BLE event mapping are unit-tested with a fake clock and fake BLE transport - **test-first**.
- Screens get a render test; mock at the feature-hook seam, never a live Supabase or a real BLE device.
- Anything BLE, background, or permission related also goes through on-device QA ([qa_protocol.md](qa_protocol.md)).
